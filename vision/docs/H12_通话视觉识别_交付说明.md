## 一、这一卡的核心不是"识别"

识别本身用现成 YOLO 就够。任务卡真正把验收压在**三条数据流边界**上：

| # | 边界 | 要求 | 本卡怎么做到 |
|---|---|---|---|
| ① | 原始帧 | 内存生成 → 实时识别 → 立即丢弃，全程不落盘 | 函数内无任何写文件/上传路径；静态扫描 11 条禁止模式 |
| ② | 识别结果 | 结构化入用户画像，**只写 confidence ≥ 0.7 的字段** | 阈值卡在写入前，不是"写进去再打标" |
| ③ | 图谱/记忆箱 | 零写入（与 H-2 持续感知严格隔离） | 源码里没有这两个路径；运行时只新增 `user_profile.jsonl` |

**为什么边界比识别难：** 识别做不准，用户觉得"小忆没看懂"；边界做错，就是"通话里的东西被记进了家里的空间记忆"。后者是隐私事故，不可回滚。

## 三、三个诚实的设计取舍（重要）

### 1. 表情：MVP 不做表情识别，而且是**明说的**

任务卡要"开心/困惑/低落"。但：
- 老人表情数据少、医疗级标注缺
- 光照/角度干扰大，YOLO 检测不到的"微表情"根本无从判断
- **误判代价极高**：判错情绪 → 进画像 → 下次对话用错语气

所以本卡的做法是：**没有可靠信号就不写这个字段**（不是写 `unknown`，写 `unknown` 也是编造一种状态）。
目前唯一给的结论是"画面极暗 → 建议放慢语速"，且**置信度刻意压在 0.6（低于 0.7）→ 不进画像**，只影响语速。

> 这一步会把任务卡"表情识别"这项标成"部分实现"。这是有意的降级，理由写在注释里，而不是假装做到了。

### 2. 注视/在场：用几何启发式，并标 `gaze_source: heuristic`

不引入人脸关键点模型（依赖重）。用"人脸框面积占比 + 是否居中"粗判：
- 面积 > 6% 且水平居中（±18%）→ `gaze: screen`
- 否则 → `gaze: away`

**标签里写明 `heuristic`**，下游知道这是粗信号，不能当结论用。

### 3. 场景不猜

帧源给 `scene: "unknown"`（真机摄像头拿不到场景），**按"没给"处理**，不写进画像。
把"不知道"写进档案 = 把不确定性伪装成事实。

## 七、已知限制

1. **表情未实现**（见第三节）。要补需要老人表情数据集，不是工程问题。
2. **单帧耗时在真机 CPU 上波动大**：首帧 4.76s（模型加载），之后 0.04s。但如果在别的机器上 CPU 更弱，可能每帧 1-2s。**建议通话时 2-3 秒一帧**，不要每帧都识别。
3. **调用频率要控制**：`observe()` 内部 append 一条画像记录。24 小时通话 × 每秒一帧 = 8 万条，无意义。上层要控频（建议 ≥2s 一次，或只在"状态变化"时识别）。
4. **后端接口未端到端联调**：本机 venv 无 fastapi，只做语法校验。
5. **`hints` 接口目前返回空数组**：意图是"实时提示"，但真正的实时提示需要和通话主循环共享同一份内存状态。当前设计是通话进程内直接调 `call_vision.observe()` 拿 `hints`，不走 HTTP。HTTP 这个接口留给"跨进程/前端读"，目前无数据源，返回空是诚实的（不造假）。

## 八、给 H-1 通话页 / 对话层的接入方式

通话主循环里（后端进程内，不是浏览器）：

```python
from call_vision import call_vision

# 每 2-3 秒一次
out = call_vision.observe(frame, call_id, scene=None)
del frame                       # 帧用完即弃

# 拿话术方向 + 语速
hints = out["hints"]            # ['person_left', 'not_gazing', 'hand_object']
speed = out["speed_hint"]       # 0.70 / 0.80 / 0.85 / 0.95

# 传给对话模型/ TTS
tts(text, speed=speed)
```

老人说"把通话里看到的忘掉"：

```python
call_vision.forget(call_id)     # 或 forget(None) 全删
```
